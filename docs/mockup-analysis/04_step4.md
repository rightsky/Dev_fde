## 1. 화면 목적

STEP 3에서 DCAT/PROV-O 카탈로그가 작성된 작업 조합(`state.combo`)의 각 데이터셋에 대해 다음을 수행한다.

1. **F축(F1~F6) 분류 배정**: "무엇에 관한 데이터인가"(주제·유형·해상도·이용조건·AI활용목적·거버넌스). 규칙엔진·임베딩 유사도(ko-e5-large)·sLLM 재순위로 프리필된 후보를 작업자가 검수하고 확정한다.
2. **K축(K1~K9) 연계키 배정**: "무엇과 조인되는가". 컬럼 메타데이터에서 규칙으로 도출된 결과를 검수한다.
3. **N2SF 보안등급(C/S/O) 지정**: 정책 옵션이 켜져 있을 때만 노출되는 단일 선택 축.
4. **데이터셋 단위 분류 확정**: `dsDone4[데이터셋명] = true`. prov:Activity 기록 대상.
5. **데이터셋 간 관계 선언 2종**
   - SSOT 우선순위 목록: 연계키로 연결되는 상대 데이터셋의 순위 목록 (LPG `JOINED_ON`).
   - 연관데이터셋: 데이터셋 2개 묶음 (LPG `GROUPED_WITH`). 이 값이 STEP 5의 완료 조건이 된다.
6. 미분류·저신뢰 추론분은 검수 큐로 집계하고, 분류체계(축·코드) 자체의 개정은 관리 평면에서 승인 절차로 처리한다.

단계 담당 조직(공통 바 알림 기준): STEP 4 = `메타데이터 표준화팀`, 다음 단계 STEP 5 = `데이터 품질관리팀` (L1682, L2989).

## 7. 실제 제품에서 필요한 기능

### 7.1 백엔드 기능

1. **분류체계(통제어휘) 저장소**: 축·코드·버전·상태를 PostgreSQL에 두고 SKOS(`skos:ConceptScheme`/`skos:Concept`, `skos:prefLabel@ko`, `skos:notation`, `owl:deprecated`)로 직렬화(rdflib). STEP 4 칩, SHACL Shape, 카탈로그 표기가 모두 이 저장소를 참조.
2. **변경 요청·승인 워크플로**: 축 추가, 코드 추가, 코드 폐기(deprecated: 기존 배정 유지 + 신규 배정 차단), 규칙 개정. 요청자·사유·승인자·결과를 남기고 승인 시 축 버전 증가, `ACT-TX-####` prov:Activity 발급, SHACL `sh:in` 목록 재생성, 벡터 인덱스 재색인.
3. **자동 분류(프리필) 파이프라인**
   - K축: 실제 스키마(컬럼명·타입·프로파일)에 대한 규칙 매칭. 결과 = 키 + 매핑 컬럼 + 근거 + 신뢰도.
   - F축: 데이터셋 문장화 텍스트를 ko-e5-large로 임베딩해 코드 임베딩과 코사인 유사도 계산(pgvector) → 상위 후보를 sLLM이 재순위 → 스키마 제약 JSON으로 제안 저장.
   - 임계값 정책: 80 이상 강추천, 40~79 검토, 15 미만 해당 없음. 필수 축 미배정 또는 임계 미달은 검수 큐 항목 생성.
   - F5는 제안 없음(작업자 직접 선택).
4. **데이터셋 × 축 배정 관리**: 배정마다 출처(rule/embedding/llm/manual)·신뢰도·상태(제안/검수 필요/확정/미분류)·근거 문서를 보관. F2~F5도 데이터셋별로 분리 저장.
5. **축 간 정합 검사**: F3 시간 해상도 ↔ STEP 3 `dcat:temporalResolution`, F4 ↔ `dcterms:license`, F6 ↔ prov:Agent 연결, N2SF 등급 ↔ 발행 구역.
6. **분류 확정**: 필수 축(F1·F2·F4·F6·K, N2SF 정책 적용 시 포함) 충족 검증 후 확정. 미충족 시 거부 또는 사유 입력 후 경고 확정. 확정·해제마다 prov:Activity(주체, 시각, 변경 전후 diff) 기록.
7. **RDF 반영**: 확정 배정을 정본 그래프에 트리플로 추가(4.5절 제안 매핑)하고 pySHACL로 검증. Shape 예: `ClassificationShape`(필수 축 `sh:minCount 1`, 값은 해당 스킴 소속 개념, deprecated 개념 신규 배정 금지), `N2SFZoneShape`.
8. **하류 무효화**: 확정 이후 배정·확정 상태·연계키·관계가 바뀌면 STEP 6 검증 결과를 stale 처리하고 STEP 7·8 산출물을 무효화(목업의 `invalidateDownstream('catalog', …)`와 같은 효과) + 감사 로그.
9. **관계 관리**: SSOT 우선순위 목록(순서 보존, 자기 참조·중복 방지, 제거 시 순서 유지), 연관 쌍(무방향·중복 방지). 확정 시 LPG에 `JOINED_ON`(속성: 연계키, 매핑 컬럼 쌍, 결합 후보 수, 순위)·`GROUPED_WITH` 엣지 투영. 결합 후보 쌍 수는 실제 데이터 프로파일로 계산.
10. **검수 큐**: 미분류·저신뢰·N2SF 미지정 항목의 담당자 배정, 필터, 페이지네이션, 처리(확정/반려) 시 자동 제거, 데이터셋·축 딥링크.
11. **재검토 요청**: STEP 5에서 접수된 변경 요청을 STEP 4에서 승인·반려하고 양쪽 동기화.
12. **지표 집계**: F1 커버리지, F2·K 평균 배정 수, 미분류 건수를 실제 집계.

### 7.4 프런트엔드(React) 구현 시 유의점

- 칩 목록은 `GET /api/taxonomy/axes/{axis}/codes`에서 받아 렌더링. 유사도·등급·`AI 제안` 배지는 제안 API 응답으로 표시.
- F1 칩은 `<label>` 안의 읽기 전용 체크박스에 label 클릭 핸들러가 걸린 구조다. 환경에 따라 클릭이 두 번 전달될 여지가 있으므로 제어형 체크박스 `onChange`로 구현한다.
- 축 카드 상태 배지(`검수 필요`·`미분류`·`확정`)와 관계 맵 엣지 색·라벨은 배정 상태에서 계산한다.
- 관계 맵은 F3·N2SF 노드도 포함하도록 확장을 검토(목업 맵에는 F3·N2SF가 없다).
- `다음 (확정)`은 미확정 데이터셋이 남아 있으면 경고 또는 차단 정책을 정해야 한다(목업은 무조건 통과).

### 7.5 결정이 필요한 불일치 목록

1. F6 코드: STEP 4(`기관 내부 관리`·`기관 간 공동`·`위탁 운영`·`민간 제공분`) vs 관리 마스터(`기관 내부 관리`·`부처 공유`·`대국민 개방`·`통제`).
2. F1 카디널리티: 카드 헤더 `필수 · 다중` vs 관계 맵 `필수 · 단일 · 확정`.
3. F4 표현 단위: STEP 4 `공공누리 2~4유형` 1칩 vs 마스터 3코드, `비공개` 누락. F4 단일/다중 여부 미표기.
4. F3 라벨 체계: STEP 4 `공간: 도로링크 단위`·`시간: 5분 (PT5M)` vs 마스터 `도로링크`·`5분`. 공간·시간을 한 축에 둘지 분리할지.
5. K 라벨: `K6 차량` / `K6 차량ID`, `K5 도로링크` / `K5 도로링크ID`.
6. 고정 데이터의 비표준 값 `F4: 기관 간 공유`, `F5: 품질진단`.
7. N2SF를 정규 축(예시 `F7 보안등급`)으로 편입할지, 정책 옵션 축으로 둘지.
8. `관리하기 →`의 이동처(문구는 검수 큐, 실제는 분류체계 관리 탭).
9. STEP 4 완료 기준: 1건 이상 확정(목업) vs 전 데이터셋 확정.
10. STEP 5 완료 조건이 STEP 4의 연관 쌍(`relPairs`)에 묶여 있는 구조를 유지할지.
