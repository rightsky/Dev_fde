> 분석 대상: `src/markup.html` 2427–3838행, `src/logic.js` `renderVals()` (357행 이후) 및 핵심 헬퍼(1–356행).
> 표기 규칙: 화면 문구는 원문 그대로 인용한다. `logic.js:NNN`은 logic.js의 행 번호, `markup:NNN`은 markup.html의 행 번호다.

### 0.1 평면 전환과 상태

| 항목 | 내용 | 근거 |

### 0.2 토스트 규칙

| 종류 | 문구 템플릿 | 근거 |
|---|---|---|
| 기본 토스트 | `✓ prov:Activity {toastId} 기록됨` | logic.js:1708 |
| `showToast()` | `toastId = 'ACT-K-' + (400 + floor(random*99))` 4자리 패딩. 즉 `ACT-K-0400`~`ACT-K-0498` 중 무작위. 2.2초 표시 | logic.js:45–50 |
| 텍스트 토스트 | `state.toastText`가 있으면 그 문구를 그대로 표시 | logic.js:1708 |

`showToast()`의 ID는 무작위 값이라 세션 시퀀스(`ACT-K-0421`~, 6.3절 참조)와 무관하고 `actLog`에도 남지 않는다. 화면에서 "기록됨"이라고 표시되는 대부분의 관리 행위는 실제로는 어디에도 기록되지 않는다.

## 1. 평면 B: 데이터 패브릭 관리 (`assets`)

### 1.1 화면 목적

데이터 평면(자산 매트릭스)과 처리 평면(AI 모델, 규칙엔진, 외부연계)을 한 화면에서 관제한다. 헤더 설명 원문: `데이터 평면(자산 매트릭스)과 처리 평면(AI 모델 · 규칙엔진 · 외부연계)을 한 곳에서 관리합니다. 사람 · 권한은 시스템 관리에서 다룹니다.`

### 2.5 데이터와 계산 규칙

#### (a) 목록 행 생성 (logic.js:482–510)

원본은 "저장된 프로세스들의 조합 스냅숏" + "현재 작업 조합"이다. 이미 발행된 1,842건(BASE)은 목록에 한 건도 나오지 않는다.

```
srcs = [ ...procList.map(p => {proc:p.name, dss:p.snapshot.combo, saved:true}),
         {proc: procName || '현재 프로세스', dss: combo, saved:false} ]
데이터셋 이름(ds.n) 기준 중복 제거 (먼저 나온 프로세스 우선)
```

| 열 | 규칙 |
|---|---|
| `id` | 저장 프로세스 소속이면 `DST-민팅 대기`, 현재 작업이면 `DST-신규` |
| `title` | `ds.n` |
| `cls` | 이름이 `/cctv\|kma\|telemetry/i`에 맞으면 `dcat:DataService`, 아니면 `dcat:Dataset` |
| `tax` | 아래 `kOf2` 표 |
| `ver` | `1.0.0` 고정 |
| `zone` | 스트림이면서 이름에 `cctv` 포함 → `통제`, 그 외 → `통제+개방 ◀` |
| `pub` | 저장 프로세스 → `발행 대기 (URI 민팅 후)`, 현재 작업 → `작성 중 ({프로세스명})` |

`kOf2` 분류·연계키 규칙 (위에서부터 첫 일치 적용, logic.js:486):

| 순서 | 조건 | 표시 값 |
|---|---|---|
| 1 | 이름 = `cctv.vehicle.det.v1` | `교통물류 · K5 K6 K7` |
| 2 | 이름 = `kma.aws.obs.v1` | `기상 컨텍스트 · K7 K3` |
| 3 | `/도로/` | `도로 · K5 K3` |
| 4 | `/사고/` | `교통물류 · K2 K7` |
| 5 | `/기상/` | `기타 · K7` |
| 6 | `/오픈마켓\|eTAS\|운행/i` | `교통물류 · K7` |
| 7 | 그 외 | `교통물류 · K7` |

STEP 3에서 입력한 메타(publisher, mediaType)나 STEP 4에서 확정한 F·K 분류는 목록에 전혀 반영되지 않는다. 클래스 판정 정규식도 `META_TABLE`의 `kind:'stream'`(logic.js:106–116)과 다르다. 예를 들어 `실시간교통사고`는 정본에서는 스트림(SVC)이지만 목록에서는 `dcat:Dataset`으로 표시된다.

#### (b) 산출물 저장소 행 생성 (logic.js:810–860)

포맷 4종:

| 태그 | 파일 접미 | MIME | 생성 함수 인자 |
|---|---|---|---|
| `TTL` | `.ttl` | `text/turtle` | `ttl` |
| `JSON-LD` | `.jsonld` | `application/ld+json` | `jsonld` |
| `문장화` | `_문장화.txt` | `text/plain` | `txt` |
| `스키마` | `_schema.json` | `application/json` | `schema` |

| 항목 | 규칙 |
|---|---|
| 그룹(프로세스) | 저장 프로세스(현재 이름과 같은 것은 제외) + 현재 프로세스. 현재 그룹명은 `{이름} (진행 중)`, STEP 8 진단 완료 후에는 `{이름} (종료)` |
| 파일명 | `base + 접미`, `base = ds.n`에서 한글·영문·숫자 외 문자를 `_`로 치환 후 앞 32자 |
| 저장 위치 | `s3://lake-ctrl/catalog/serialized/{파일명}` (표시용 문자열) |
| Activity 표기 | 저장 프로세스: `ACT-SER-{프로세스 id(타임스탬프) 끝 4자리}`. 현재: STEP 8 완료 시 `ACT-K-{actSeq 4자리}`, 아니면 `ACT-미발급`. 뒤에 ` · #{체크섬 8자}` |
| 체크섬 | `hash32hex(JSON.stringify(buildCanonical(ds)))` (FNV-1a 32비트, 16진 8자리. logic.js:140, 289) |
| 게이트 문구 | 저장 프로세스 → `완료 · 저장 확정` / 현재 + 변환 완료 → `STEP 6 검증 ✓ · 파생 자가검증 ✓` / 그 외 → `STEP 7 변환 대기` |
| 행 수 | 데이터셋 수 × 4 |

파일 내용은 저장된 것이 아니라 다운로드 시점에 정본 엔진(`mkContentFor`, logic.js:280–288)이 매번 새로 만든다. 그래서 변환(STEP 7)을 한 번도 실행하지 않았어도 조합에 데이터셋만 있으면 4개 파일 행이 `STEP 7 변환 대기` 상태로 나오고 다운로드도 된다. ID는 현재 모드에 따라 초안 ID(`DST-draft-…`) 또는 민팅 ID가 들어간다(6절).

#### (c) 프로세스 저장 엔트리 구조 (logic.js:936–945)

```json
{"id": 1724223456789, "name": "1차 프로세스", "savedAt": "08-21 07:07", "step": 7, "ver": 2, "count": 3, "done": true, "snapshot": { "combo": [], "…": "workKeys 40여 종" }}
```

`savedAt`은 `new Date().toISOString().slice(5,16)`이므로 UTC 기준 `MM-DD HH:MM`이다(logic.js:931). 화면의 다른 시각(`nowHM`)은 로컬 시각이라 9시간 차이가 난다.

#### (d) KPI와 세션 집계 (logic.js:577–581, 644)

`sessCnt` = 저장 프로세스 전체 조합 + 현재 조합의 데이터셋 이름 합집합 크기. `pubCnt`·`openCnt`는 상수 BASE(3.4절).

### 2.6 스튜디오 산출물이 카탈로그에 나타나는 방식 (요약)

| 스튜디오 사건 | 카탈로그 반영 |
|---|---|
| STEP 2 조합에 데이터셋 추가 | 목록에 `DST-신규` · `작성 중 ({프로세스명})` 행 추가, 산출물 저장소에 4파일 행(`STEP 7 변환 대기`), `등록 대기 (세션)` +1 |
| STEP 7 변환 완료 (`convertState='done'`) | 현재 그룹 게이트 문구가 `STEP 6 검증 ✓ · 파생 자가검증 ✓`로 변경. 자가검증 전부 통과 시 프로세스가 `done`으로 자동 저장됨(logic.js:2931–2934) |
| 프로세스 저장 (`procSave`, 자동 저장 포함) | 해당 데이터셋 행이 `DST-민팅 대기` · `발행 대기 (URI 민팅 후)`로 바뀜. 프로세스 관리에 행 추가 |
| STEP 8 진단 완료 | 현재 그룹명이 `(종료)`로, Activity 표기가 `ACT-K-####`로 변경 (logic.js:822, 1618–1630) |
| 발행 승인 | 구현 없음. 어떤 행도 민팅된 `DST-######`과 발행일을 가진 "발행 정본"으로 전환되지 않는다. `발행 데이터셋 1,842`도 변하지 않는다 |

### 2.8 실제 제품에서 필요한 기능

#### 기능 요구

1. 발행 정본 저장: 발행 승인 시점에 정본(canonical JSON)과 RDF 그래프(rdflib, 데이터셋별 named graph)를 불변 버전으로 저장한다. 식별자는 민팅된 안정 URI(6절).
2. 목록 조회: 서버 페이지네이션, 정렬(발행일, 제목, 식별자).
3. 검색: 제목·식별자·키워드·설명 전문 검색. 한국어는 `pg_trgm` 또는 bigram 인덱스를 권장한다.
4. 필터: 목업 칩에 대응하는 최소 집합은 F1 주제(`교통물류` 등), 클래스(`dcat:Dataset` / `dcat:DatasetSeries` / `dcat:DataService`), 실시간 여부, 구역(통제 / 개방 투영 포함). 여기에 N2SF 등급, 발행 기관, K 연계키를 더한다.
5. 상세 조회: 목업 상세의 6개 섹션을 정본에서 채운다. 필드 매핑은 아래 표.
6. 표현 협상: `text/turtle`, `application/ld+json`, 문장화 텍스트, JSON Schema를 발행본 기준으로 제공한다. 발행 시점에 생성·보관하고 체크섬을 기록한다.
7. 배포본 체크섬 대조(`spdx:checksum`) 결과 표시.
8. 리니지 링크(PROV 그래프), 적용 Plan 링크.
9. 상태 구분: 작성 중(초안 ID), 발행 대기(민팅 전), 발행됨. 목업의 `DST-신규` / `DST-민팅 대기` 행은 "발행 정본" 목록과 분리된 "등록 대기" 탭으로 옮기는 편이 맞다.
10. 개방구역 투영: 발행본에서 필터 규칙(`샘플 레코드 제외 · 프로파일 통계 제외`)과 N2SF 게이트를 적용한 부분집합을 단방향 push하고 건수를 집계한다.
11. 산출물 저장소: 프로세스 단위 아티팩트(4포맷)를 객체 스토리지에 실제 저장하고, 다운로드 시 `prov:Activity`를 기록한다.
12. 프로세스 수명주기: 소프트 삭제(휴지통), 복원, 영구 삭제. 권한과 감사 기록 필수.

### 6.1 핵심 발견: 민팅 정책 화면은 목업에 없다

- 스튜디오 로직은 "관리 탭 민팅 정책"을 두 번 참조한다. 수정 라우팅 상수 `FIX_ROUTE.mint = { step: 2, label: 'ID 발급 안내 · 관리 탭 민팅 정책' }`(logic.js:131)와 게이트 0 ④ 실패 문구 `민팅 미등록 데이터셋 존재 — fallback 발급 금지 · 게이트 0 ④ FAIL (관리 탭 민팅 정책에서 등록 후 재검증)`(logic.js:2749).
- 그러나 시스템 관리의 탭은 1~7, 9, 10뿐이고(5.2절) 민팅과 관련된 컨트롤이 하나도 없다. markup 2427–3838행에서 "민팅"이 나오는 곳은 카탈로그의 안내 문구 두 줄(markup:2930, 2973)뿐이다.
- 민팅 규칙은 logic.js의 헬퍼와 STEP 8의 `URI 민팅 (채번)` 안내 박스(markup:2315–2322)에만 있다. 아래는 그 규칙을 전부 모은 것이다.

따라서 실제 제품에서는 민팅 정책 화면을 새로 설계해야 한다. 비어 있는 `admTab` 8 자리를 쓰는 것이 자연스럽다(6.6절은 목업에 없는 제안이다).

### 6.3 로직에 구현된 규칙

#### (a) 초안 ID: 이름 기반 결정적 해시 (logic.js:139, 150–162)

```
hash6(str) = ( Σ charCode(ch) × 31 ) mod 999999  → 6자리 0 패딩
초안 ID    = {KIND}-draft-{hash6(데이터셋명)}
KIND       = 'DST' | 'DIST' | 'ACT'. 단 kind='DST'이고 META의 kind가 'stream'이면 'SVC'
```

| 리소스 | 초안 ID 형식 | 예 |
|---|---|---|
| 데이터셋 본체 | `DST-draft-XXXXXX` | |
| 스트림 본체 (dcat:DataService) | `SVC-draft-XXXXXX` | |
| 배포본 | `DIST-draft-XXXXXX` | |
| 생성 활동 | `ACT-draft-XXXXXX` | |

주의점:
- `hash6`은 문자 코드의 합이라 글자 순서가 달라도 값이 같다. 글자 구성이 같은 이름끼리 충돌한다. 초안 ID의 유일성을 보장하지 못한다.
- 같은 이름이면 본체·배포본·활동의 해시 부분이 모두 같고 접두만 다르다.
- 스트림 판정은 `item.meta` 또는 `META_TABLE[이름]`의 `kind`만 본다. STEP 3에서 사용자가 덮어쓴 값(`metaOver`)은 접두 결정에 쓰이지 않는다(logic.js:159).

#### (b) 발행 모드 ID: 민팅 맵 조회 (logic.js:117–123, 152–157)

`state.pubMode === true`(STEP 7의 토글 `발행 전 (초안 ID)` / `발행 후 (민팅 적용)`, logic.js:2755–2763)일 때만 적용된다.

민팅 맵 `MINT_MAP` 전체:

| 데이터셋명 (키) | 민팅 ID |
|---|---|
| `kma.aws.obs.v1` | `SVC-000041` |
| `cctv.vehicle.det.v1` | `SVC-000042` |
| `sample_공간정보_통합포털_데이터셋_목록_도로` | `DST-000961` |
| `실시간교통사고` | `SVC-000043` |
| `디지털운행기록분석시스템(eTAS)_정보시스템` | `DST-000962` |

```
mintId(item, kind):
  m = MINT_MAP[이름]            (simMode='nomint'이면 조합 첫 항목은 강제로 미등록 처리)
  m 없음           → null       (대체 발급 금지)
  kind = 'DST'     → m          예: DST-000961, SVC-000041
  kind = 'DIST'    → m + '-DIST' 예: DST-000961-DIST
  kind = 'ACT'     → m + '-ACT'  예: SVC-000041-ACT
```

- 하위 리소스 ID는 본체 ID에 접미사를 붙인다. 독립 시퀀스(`DIST-000961`)가 아니다.
- 맵에 없는 데이터셋은 정본에 `DST-미민팅-{hash6}` · `ACT-미민팅-{hash6}` · `DIST-미민팅-{hash6}` 자리표시 ID가 들어가고 `_minted=false`가 된다(logic.js:171, 176, 181).
- `META_TABLE`(logic.js:106–116)에는 9건이 있지만 `MINT_MAP`에는 5건뿐이다. 나머지 4건(`sample_교통사고심층조사시스템_비정형_`, `sample_데이터오픈마켓(30종)`, `sample_디지털운행기록분석시스템(eTAS)`, `sample_실시간기상관측자료수집시스템_기상청_`)은 발행 모드에서 항상 게이트 실패다.

#### (c) 게이트 0 ④: 등록 규칙의 집행 지점

| 위치 | 규칙 | 문구 |
|---|---|---|
| `validateDs` (logic.js:313) | `pubMode && !c._minted` → 실패, 라우트 `mint` | `게이트 0 ④ — 민팅 미등록 (fallback 발급 금지)` |
| STEP 6 게이트 표시 (logic.js:2742–2751) | `g4 = !published \|\| 조합 전체가 MINT_MAP에 있음` | 통과(발행 모드): `민팅 적용 — (-신규\|-draft-) 잔존 0건 (실시간교통사고 = SVC-000043 · eTAS = DST-000962 · kma = SVC-000041)` |
| | | 실패: `민팅 미등록 데이터셋 존재 — fallback 발급 금지 · 게이트 0 ④ FAIL (관리 탭 민팅 정책에서 등록 후 재검증)` |
| | | 초안 모드: `초안 ID(결정적 해시) 상태 — 데이터셋별 고유(KIND-draft-XXXXXX) · 발행 시 민팅 ID로 치환 · 발행 산출물에는 (-신규\|-draft-) 잔존 불가` |
| 요약 배지 | | `게이트 0(의미·형상) 통과 — SHACL 진행 가능` / `게이트 0 ④ 실패 — 민팅 미등록` |
| 수정 라우팅 (logic.js:131) | 위반 → STEP 2로 안내 | `ID 발급 안내 · 관리 탭 민팅 정책` |

정리하면 목업의 등록 규칙은 다음과 같다.
1. 초안 단계에서는 결정적 초안 ID로 작업하고 게이트 0 ④를 통과한다.
2. 발행 단계에서는 사전에 등록된 민팅 ID가 있어야 한다. 없으면 실패하고 시스템이 임의로 번호를 만들어 주지 않는다.
3. 발행 산출물에는 `-신규` 또는 `-draft-` 문자열이 남아 있으면 안 된다.
4. 발행된 ID는 바뀌지 않는다.
5. 모드 전환은 정본을 바꾸지 않으므로 검증 결과를 무효화하지 않고 게이트 0 ④만 다시 평가한다(logic.js:2755–2760).

### 6.6 실제 제품 요구사항 (제안: 목업에 없는 부분 포함)

#### (a) 정책 원칙

1. 임시 ID와 안정 ID를 분리한다. 초안은 서버가 만든 내부 UUID를 키로 쓰고, 화면 표시용 초안 ID(`DST-draft-…`)는 UUID에서 파생한다. 이름 해시는 쓰지 않는다.
2. 안정 ID는 발행 승인 트랜잭션 안에서만 발급한다. 형식은 `{PREFIX}-{6자리 0 패딩}`, IRI는 `https://catalog.molit.go.kr/id/{경로}/{ID}`.
3. 발급은 PostgreSQL 시퀀스(접두별 1개)로 하고 재사용하지 않는다. 롤백으로 생긴 결번은 허용한다.
4. 발급된 ID는 불변이다. 폐기는 삭제가 아니라 무효화(`prov:wasInvalidatedBy`)로 처리하고 번호는 영구 예약 상태로 둔다.
5. 자연키(예: 발행 기관 IRI + 원천 시스템 식별자 또는 정규화된 제목)로 멱등성을 보장한다. 같은 자연키로 다시 요청하면 기존 ID를 돌려준다.
6. 미등록 상태에서 대체 발급을 하지 않는다는 목업 원칙을 유지한다. 구체적으로는 "민팅 정책에 해당 리소스 유형의 스킴이 활성화되어 있고, 발행 요청이 승인되어 ID가 예약(reserved)된 상태"가 아니면 게이트 0 ④에서 실패시킨다.
7. 발행 직전 최종 검사: 직렬화 결과 전체에서 정규식 `(-신규|-draft-|-미민팅-)` 일치 0건.
8. 치환 맵(초안 ID → 안정 ID)을 `prov:Activity`와 함께 저장한다.
